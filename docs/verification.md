## Deployment and restoration boundary

The host used here is macOS/Apple Silicon with Socktainer over Apple Container, rather than the user's x86 Linux LXC. `docker compose -f docker-compose.yml -f docker-compose.dev.yml config --quiet` passes. The locally built app and engine images boot and pass health/API smoke checks. The final app image created an administrator, reached the private 278-source registry and wrote CBZ and EPUB fixtures as its configured nonroot application UID.

Socktainer's compatibility layer exposed three local limits: it did not consistently resolve locally tagged image IDs when Compose constrained the runtime architecture; newly created volumes do not inherit image directory ownership as standard Docker copy-up does; and its multi-network service DNS was unreliable. The successful local image smoke used initialized named volumes and direct container IPs. The production Compose retains normal Docker service DNS, nonroot engine restrictions and guest bind paths. No change to the user's actual Proxmox cluster or reverse proxy was made. At the time of that verification, no image or remote GitHub fork had been published.

The full backup script successfully archived PostgreSQL, configuration, CBZ/EPUB directories, enabled novel sources and Suwayomi state. Restore initially met macOS bind-mount ownership/time restrictions. Running the same restore implementation with disposable named volumes completed. The restored database had the same 41 public tables and server-settings row as the backup; the actual EPUB and CBZ bytes matched exactly. Empty top-level filesystem `lost+found` directories are preserved and tolerated; populated destinations and corrupt manifests are refused.

The committed Linux workflow additionally boots the actual Compose topology, seeds standard books, takes a full backup and restores it into a separate project with empty bind directories. The [first published run](https://github.com/samitaaissat/Miaoyomi/actions/runs/33967318606) reached restored service health and account setup checks, then failed while comparing restored EPUB bytes because the runner user could not read the file. That Compose verification failure is separate from the successful native-installer job.

## Native Proxmox installer boundary

The native installer is a separate deployment path from the Compose builds and restore tests above. It creates a new unprivileged x86_64 Alpine 3.24 LXC and runs the app, novel engine, PostgreSQL 18 and Suwayomi as native OpenRC services. Its default solver path delegates creation of a separate Debian LXC to the official community installer. Neither guest runs an inner container runtime. The app's optional nesting feature setting is independent of this deployment model; the solver keeps upstream feature settings. The installer does not convert existing Compose volumes, and the Compose backup/restore test does not validate native archive recovery.

Package and launch requirements were checked against primary sources on 2026-09-05. The official Alpine 3.24 [main repository](https://dl-cdn.alpinelinux.org/alpine/v3.24/main/x86_64/) contains Node 24 and PostgreSQL 18; its [community repository](https://dl-cdn.alpinelinux.org/alpine/v3.24/community/x86_64/) contains `openjdk25-jre-headless`. The pinned [Suwayomi v2.3.2243 release](https://github.com/Suwayomi/Suwayomi-Server/releases/tag/v2.3.2243) provides the standalone JAR with SHA-256 `821141b32e170d4a02d3cbdfed577ed8f07bd22383ff5f4132ebb5ae40e98dd5`. Headless startup explicitly disables KCEF, system tray and browser opening; extension workflows requiring WebView are outside this installation's supported runtime.

The [official FlareSolverr CT script](https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/flaresolverr.sh), [native Debian installer](https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/install/flaresolverr-install.sh) and [community PVE backend](https://raw.githubusercontent.com/community-scripts/core/main/pve/backend.func) were inspected on 2026-09-05. The current script selects Debian 13, installs Chrome and a native systemd service, and provides an official update path. Miaoyomi's app defaults remain 6144 MiB RAM/32 GiB disk; solver resources belong to its separate LXC. An existing local native solver or an external endpoint can be reused instead. A new official solver wizard requires a terminal and is rejected with `--yes`.

The host wrapper manages address discovery and delegates app/Suwayomi configuration changes to `miaoyomi set-solver`, which checks reachability, backs up and preserves unrelated settings/secrets. `--update-solver` runs the official updater inside a local solver before reconnecting; `--reconnect` refreshes the endpoint independently. App updates retain the connection without upgrading the solver. App backups contain connection metadata, not data from the solver guest. FlareSolverr's separate browser does not enable Suwayomi KCEF or novel-plugin browser access.

Local verification on 2026-09-05 passed: Bash syntax and ShellCheck for both installers; **54 host/guest behavior tests**; **9 BFF solver, concurrency and manga-page regressions**; the BFF TypeScript build; and the real-checkout installer dry run. The installer tests cover cancellation, container identity, inter-LXC connection failure, configuration preservation, manager replacement, log permissions and interrupted backup/cutover recovery. CI runs the installer lint and behavior checks in its `native-lxc-scripts` job.

After publication of `main` at `d7d18886e917f33a882a03a03dbfd33039e29e82`, the live raw installer passed Bash syntax, `--help` and remote-mode `--dry-run` checks from outside a checkout. An anonymous shallow clone/fetch succeeded. Its source archive retained all 13 required installer/build inputs and all 278 vendored novel scripts with matching registry hashes; all three lockfiles resolve packages through the public npm registry. The [published native-installer CI job](https://github.com/samitaaissat/Miaoyomi/actions/runs/33967318606) passed. Native installation does not require a release tag or image publication.

The remote-path follow-up adds an automated check for the default public repository and explicit ref selection outside a checkout. Both installers pass Bash syntax and ShellCheck, and the combined host/guest suite passes **55 tests**.

The first reported real-node attempt then exposed a host permission bug: the installer's global `umask 077` caused Proxmox to create `/var/lib/lxc/600` without traversal permission for its mapped extraction UID. A disposable Linux reproduction using Perl `File::Path` and GNU tar as UID 100000 reproduced the exact `Cannot open: Permission denied` failure with a `0700` parent, and succeeded with a `0755` parent. Proxmox [creates the directory with `make_path`](https://github.com/proxmox/pve-container/blob/1c0488315a1df22a9bba635a81e7543b5ce664b7/src/PVE/LXC.pm#L1833-L1855) before [extracting through the mapped namespace](https://github.com/proxmox/pve-container/blob/1c0488315a1df22a9bba635a81e7543b5ce664b7/src/PVE/LXC/Create.pm#L171-L184). The fix uses `022` for host operations and isolates private configuration/receipt creation under `077`. Retry recovery removes only empty, root-owned, unmounted directories for an ID the cluster confirms is unused. Bash syntax, ShellCheck and **68 host/guest tests** pass, including restrictive caller permissions, private files and recovery refusals. A successful real Proxmox installation after this fix is still pending.

The fixed installer functions were also sourced and exercised in disposable Linux with real Perl directory creation, GNU tar as UID 100000, `stat`, `mountpoint` and `rmdir`; only `pct` and `pvesh` were substituted. Fresh creation and retry after empty-directory cleanup both succeeded with a restrictive caller umask. Nine unsafe cleanup cases refused removal and preserved their fixtures, including data, hidden files, symlinks and foreign ownership.

## Reproduce

Use a disposable PostgreSQL database with `TEST_DATABASE_URL` and `TZ=UTC`, then run the commands in the root README. Upstream date parsing tests assume UTC; a Europe/Paris baseline run reproduced an existing absolute-date expectation mismatch. The supplied Compose fixes `TZ=UTC` for the app. For the browser fixtures, build `web/out` and run `node web/test/e2e/novels.mjs` with Chrome available. Run `MANGA_BROWSER_DATABASE_URL=postgres://test:test@localhost:5432/miaoyomi_browser_manga node web/test/e2e/manga-immediate.mjs` against a separate disposable database for the real manga API/reader/offline flow. Both fixtures accept `PUPPETEER_EXECUTABLE_PATH` or use an installed/bundled Chrome. For EPUBCheck, generate `bff/test/helpers/generateNovelEpub.cjs` with `node --import tsx` from the BFF directory and validate the emitted path with EPUBCheck 5.3.0.

The native LXC setup and operational commands are in [deployment](proxmox-lxc.md); [backup/restore](backup-restore.md) applies to Compose only. A development server serving a static export must restart after `web/out` is rebuilt, because the upstream static route registry snapshots hashed asset filenames at boot.
